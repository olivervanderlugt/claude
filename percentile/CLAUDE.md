# Percentile — working notes for Claude Code

Consent-first analytics and a benchmark data co-op for AI-built apps. Read this before
changing anything under `src/core/privacy/`.

## Commits

Commit and push without being asked to specify a message. Never ask the user to supply
one, and never leave a placeholder for them to fill in — read the diff and write it.

Format: present tense, describing what the commit does and *why* where the why is not
obvious. State test counts when they change. If a change is a partial fix, say what is
still broken rather than implying completeness.

Work directly on `main`. This repo has no PR requirement.

## The one architectural rule

There are two data planes and they must never be conflated:

- **First-party plane** — pseudonymous, per-workspace, developer owns it, we are a
  processor.
- **Co-op plane** — aggregate-only, k-anonymised, cross-workspace, we are a controller of
  anonymous data.

`src/core/privacy/release-gate.ts` is the **only** code path between them. Every number a
third party ever sees passes through `gateRelease()`. Keeping it to one function is
deliberate: the compliance surface of the whole company stays auditable in one file.

Do not add a second path. If something needs to cross, it goes through the gate or it does
not cross.

## Invariants that look optional and are not

- **Consent is keyed on `deriveConsentAnchor`, never `deriveSubjectKey`.** Subject keys
  rotate every 30 days; keying consent on them silently expires withdrawals, and the US
  jurisdiction default is `granted`, so a withdrawn subject gets re-enrolled. Events use
  the rotating key; consent and suppression use the anchor.
- **Percentiles use the exponential mechanism, never Laplace.** Laplace needs a
  sensitivity and the intuitive `(hi-lo)/n` is correct for a mean and wrong for an order
  statistic — it decays as 1/n, so larger cohorts get less noise while true sensitivity
  stays flat. Privacy would degrade as the network grows.
- **Redaction runs before persistence.** A leak in a customer's generated code must not
  become a breach in our database.
- **Pseudonyms are keyed per workspace.** Cross-app profiling is impossible by
  construction, not by policy. Do not add anything that links a subject across workspaces.
- **Fail closed.** Unknown jurisdiction, missing consent, exhausted budget — all refuse.

## Testing privacy code

Privacy claims must be provable, not asserted. A defence gets a test that fails if the
defence is removed. Statistical tests need enough trials to be convincing — the adversarial
suite uses hundreds of draws, not one lucky sample.

`test/adversarial.test.ts` is an internal red-team suite. `VULN-*` tests pass *because an
attack works* and are evidence of a live vulnerability; `HOLDS-*` are regression guards.
Read the header comment before editing.

## Documentation honesty

`docs/` describes what the code does, not what it should do. Both audits found the docs
describing an architecture the implementation did not deliver. If you fix code, update the
doc. If you find a doc overstating, correct it rather than quietly building toward it.

Numbers in `docs/02-business-model.md` are generated by `scripts/model.ts`. Change the
assumptions, re-run, paste the real output. Never hand-edit a figure.
